# 设备连接与通信验证分离：实现及验收方案

**简体中文** · [English](device-communication-design.en.md) · [文档目录](../../docs/README.md)

## 目标与边界

TCP 握手只表示对端 TCP 栈回应，设备待机不等于故障。设备是否支持主动查询或心跳必须按型号和配置确认。默认不发送额外探测，不把静默设备和未验证设备计入故障。当前 149 不配置未经确认的探测地址或扫码器心跳。

## 状态与接口

保留现有设备状态接口及字段，增加运行时的 TCP 状态、通信验证结果、检测方式、最近请求时间/类型、连续超时次数。信息驻留在后端运行连接对象中，不增加数据库表或列。

| 状态 | 页面含义 | 故障计数 |
| --- | --- | --- |
| VERIFYING | TCP已连接，通信未验证；允许长期待机 | 否 |
| ONLINE | 最近通信成功，展示具体时间 | 否 |
| CONNECTING / RETRYING | 连接中 / 请求暂未应答，正在重试 | 否，独立统计 |
| UNKNOWN | 页面暂时拿不到服务状态 | 否，单独提示状态未知 |
| OFFLINE | TCP连接失败或已断开 | 是 |
| TIMEOUT | 已发送需要应答的请求，连续超时达到阈值 | 是 |
| DEGRADED | 设备协议拒绝读写或业务值异常 | 是；不等同于TCP断开 |

连接重建重新验证，保留历史成功时间；超时故障不能仅靠重新握手消除，需有效通信恢复。正常被动扫码器即便长时间没有数据，也不自动降级。前端完整快照重取、断线置未知、15秒定期刷新和请求乱序保护继续保留。

## 扫码器

默认被动模式，仅接收扫码、NoRead 和支持的 HeartBeat 报文，保留 TCP keepalive；移除90秒读空闲报警和默认应用层心跳发送。

通过服务配置 `device-health.scanner-heartbeats.<设备ID>` 显式启用当前 STX/HeartBeat/ETX 协议。默认间隔30秒，应答等待10秒，连续3次超时才报告通信超时。仅在请求成功发出后启动等待；有效入站报文确认通信并清零超时计数，普通写成功不能确认设备协议正常。旧通道报文、定时任务和关闭回调不能影响新通道。

## PLC

现有业务写入/回读及配置在PLC地址表中的类型5心跳写入保持原有业务含义。心跳只证明协议请求成功，不能抹去业务拒绝；不自动重放失败的业务写入，失败日志仍立即产生。

增加 `device-health.plc-probes.<设备ID>` 安全只读检测，需显式提供已确认可安全读取的 Int16 地址。默认不启用，默认间隔15秒，连续3次超时报告故障；读取结果不更新缓冲垫、不改变PLC数据、不写scan_log。沿用HSL读超时限制；同一PLC的检测和业务I/O串行，检测不堆积，同设备一次仅允许一个检测任务。

协议异常应答与传输失败分开：协议拒绝报告地址/权限问题，明确连接断开或拒绝立即标记断开；单次请求超时进入重试状态，阈值达到后报告超时并释放失效连接。所有有效协议成功都会重置超时计数。连接替换期间旧请求结果不能覆盖新连接状态。

## 配置、部署和数据库

配置保存在后端YAML或外部Spring配置文件，按设备ID配置，启用和修改需重启服务；不增加设备管理页面字段。本次不变更数据库结构、不需要升级SQL新增迁移。安装程序同步当前后端和前端构建。

配置示例（ID和地址仅演示，启用前须按实际设备确认）：

```yaml
device-health:
  failure-threshold: 3
  scanner-heartbeats:
    999001:
      enabled: false
      interval-seconds: 30
      response-timeout-seconds: 10
  plc-probes:
    999002:
      enabled: false
      address: MW10000
      interval-seconds: 15
```

扫码器开关只适用于已确认支持 `STX + HeartBeat + ETX` 应答的设备，不直接适用于其他型号的查询命令。`NoRead`和正常扫码报文也可确认通信；无法解析的字节不确认通信。心跳等待时间必须小于发送间隔；PLC启用只读检测必须提供非空地址，否则配置校验失败并阻止启动。可用 `spring.config.additional-location` 加载外部YAML，或通过已有Spring配置方式设置；不自动变更Docker挂载。

只读检测间隔从上次请求结束后计算，避免长超时积压，底层接收超时沿用当前HSL客户端设置。请求失败不回放业务写入。设备断电或拔线的发现延迟取决于TCP错误、keepalive及是否启用主动检测；未启用检测时不承诺固定时间发现静默断线。

按既有授权部署到149的 `/docker/docker-compose.yml`，前端 `/docker/nginx/bufferpad`。发布前备份镜像及前端，验证当前镜像版本，失败回滚；不改变其他服务或业务配置。

## 验收矩阵

1. 无设备回应但TCP握手成功：未验证，不显示通信成功。
2. 被动扫码器长时间静默：不发应用心跳、不报警；扫码恢复时正常处理业务。
3. 启用扫码器心跳：成功回应、无回应、连续阈值、回应恢复、旧通道回调和发送失败。
4. PLC未配置检测：不发额外请求；配置检测仅产生Int16读取，无业务写入或scan_log记录。
5. PLC有效响应、连续超时、协议异常、故障恢复、业务并发与连接替换。
6. 前端各类计数、双层状态、历史时间、断线重连及乱序保护。
7. 前后端全量自动化测试和真实TCP模拟设备验收；149至少120秒连续观测，覆盖上一版90秒误报窗口；浏览器检查默认静默设备不计入异常。
8. 登录/权限回归、构建产物一致、安装程序同步、数据库结构前后校验。
