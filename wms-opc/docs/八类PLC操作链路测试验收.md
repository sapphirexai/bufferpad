## 八类操作的验收规则

“重新扫码”对应当前系统的手动扫码入口。两小时内重复扫码仍不增加使用次数，但必须依据当前寿命判断应该向PLC通知成功还是超限。

| 类型 | 名称 | 预期行为 | 结果 |
| --- | --- | --- | --- |
| 0 | 扫码失败 | NoRead不新增缓冲垫或使用明细，向配置地址写1，一条失败汇总日志 | 通过 |
| 1 | 扫码超过最大次数 | 到达或超过寿命上限，向超限地址写1，不读成功回读地址；短时间重扫仍通知超限 | 通过 |
| 2 | 扫码成功 | 新码或超过两小时间隔计数一次，提交后向成功地址写1，再执行类型6回读 | 通过 |
| 3 | 重新扫码超过最大次数 | 手动输入保留关联扫码器，向重新扫码超限地址写1，不读成功回读地址 | 通过 |
| 4 | 重新扫码成功 | 手动输入向重新扫码成功地址写1，再执行类型7回读；无法唯一确定扫码器时不广播 | 通过 |
| 5 | 心跳 | 按已有配置周期写0，不产生扫码计数、使用明细或业务汇总日志 | 通过 |
| 6 | 扫码成功开口数回读 | 仅类型2写入成功后读取，0和32767有效，负值/异常不能保存 | 通过 |
| 7 | 重新扫码成功开口数回读 | 仅类型4写入成功后读取，主表与最新使用明细一致保存 | 通过 |

测试中的汇川PLC使用真实Modbus TCP功能码06写单个寄存器、03读寄存器。另一个模拟PLC始终不接收非目标指令。既有西门子S7模拟业务及真实TCP回环用例也纳入后端完整回归。

## 发现的问题与修改

1. **超限后短时间重扫误发成功指令。** 原逻辑先命中“两小时内重复扫码”，直接走成功通知，绕过寿命判断。现在重复扫码也先判断寿命，到达上限继续发送类型1/3，不发送类型2/4或执行类型6/7。
2. **TCP拆包、粘包导致漏码和拼码。** 原逻辑把一次网络读取当作一个完整报文。增加有长度上限的流式解帧器，支持STX/ETX和TPL包围格式、跨包UTF-8、多个连续帧、残缺帧及噪声恢复。
3. **二维码中的控制关键字被误判。** 原来使用`contains`识别NoRead和HeartBeat。现在只有完整消息内容等于控制字才作为控制消息，二维码中的同名字样仍按二维码处理；空帧、未闭合帧、过长内容和无效编码不会计数。
4. **并发首次扫码触发重复键失败。** 现在首次插入冲突后读取已提交记录，按重复扫码处理。自动与手动扫码事务使用READ_COMMITTED，避免并发越过寿命上限后仍按旧快照通知成功。唯一索引及条件计数更新继续保证只建一次、只计一次。
5. **导入的回读PLC关联不一致时会读取错误设备。** 即使配置页面已有校验，运行时也校验回读与通知是否关联同一个PLC且地址非空。不一致时提示配置异常，不把另一个PLC的地址用于当前连接。
6. **开口数保存异常后日志无法及时结束。** 现在捕获保存异常并产生同一操作的回读失败结果；明细缺失或更新失败时主表开口数一起回滚，不重放PLC写入，也不把数据库异常误报成TCP断线。
7. **使用明细时间相同可能更新较旧的一条。** 最新明细排序补充`id DESC`，相同创建时间下稳定更新最新记录。

## 重复执行

可复用脚本：`wms-opc/tools/acceptance/eight_operations.py`。依赖Java17、MySQL8服务器和客户端、Python3及PyMySQL。默认使用本工作区安装程序解包的运行时，也支持`--java`和`--mysql-bin`指定测试运行时。

在项目根目录执行：

```powershell
mvn -f wms-opc/pom.xml -s tmp/auth-maven-settings.xml -q package
python wms-opc/tools/acceptance/eight_operations.py acceptance
```

可通过`--jar`选择待验收JAR。脚本使用`tmp/eight-operations-<标签>/mysql-data`中的专用MySQL实例，只绑定127.0.0.1随机端口，只重建该实例内的`eight_operations_acceptance`库。模拟设备也只监听本机。结束时停止测试服务，保留JSON、协议收发记录、SSE及应用日志供复核。不得把脚本的数据库连接改成业务数据库。

测试中的模拟设备证明了本次覆盖范围内的服务和协议处理逻辑；现场设备固件、梯形图、实际网络故障及具体寄存器配置仍以现场联调为准。
