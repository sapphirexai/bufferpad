快速读懂（约 1 分钟）

这个系统是做什么的？

  • 产线上用扫码枪扫缓冲垫上的二维码，系统记次数（用了多少次），快到上限时提醒现场并告诉 PLC。
  • 也可以在电脑上手工补一条码（补码），规则和扫码类似。
  • 大屏/前端可以通过长连接（SSE）收到「设备连上/断开」和「扫码结果」。

记三个数字就够：

  • 2 小时：同一张码若 2 小时内又扫一次，算「无效」，不加次数（防误扫）。
  • 最大次数：可从数据库配置；超过后会给 PLC 发「超限」信号并推告警。
  • 产线号 workLine：设备和推送都按产线区分，前端 SSE 的 clientId 要跟产线号一致才能收到该线消息。

一、业务逻辑（先看场景，再看表）

所有「扫到一个码」最终都会进同一把总阀门：CushionInfoServiceImpl.onQrCodeReceived。无论是扫码枪发来的，还是网页上手动补的。

1.1 扫到一个码之后，系统怎么想？

每进来一次，会先记一条扫码日志（方便以后查「当时是谁、手动还是枪扫」）。然后按下面三种情况分流：

情况 用一句话说 接着会发生什么（方便和现场对照）
库里第一次见这个码缓冲垫主表里还没有这条二维码 新缓冲垫建档 写明「已用 1 次」、最大次数从配置读（没有配置则用默认 500）；记一条明细；告诉 PLC「成功」一类信号；有时还会从 PLC 再读开口数写回数据库。
老码，但离上次扫不到 2 小时看字段 lastScanDate 无效扫码 不加次数；通知前端（失败提示）；按规则点亮 PLC 对应位；记成异常类日志。
老码，且隔了至少 2 小时 正常再用一次 已用次数 +1；更新时间、哪把枪扫的；记明细；告诉 PLC；若已到上限再发「超限」。成功时也可能读 PLC 开口数写回库。

1.2 人工补码和「多工位一起通知 PLC」

  • 补码时没有扫码枪序号（程序里 scannerSeq 为空），位置会记成「手动」。
  • 有些情况下 PLC 要通知、但说不清是哪一个工位，就会把所有扫码器工位各通知一遍（代码里遍历 type=扫码器）。
  • 若已经知道工位序号，才会在成功后去读开口数；没有工位序号则跳过去读。

1.3 枪说「没扫到」（NoRead）

会记失败日志、给 PLC 发「失败」类型（若表里有配置地址）、并给前端推一条「失败/无码」相关的消息。

1.4 扫码枪发来的数据长什么样？（现场沟通用）

  • 带 HeartBeat → 只是保活，不当成正式条码。
  • 以特殊开头字符（如 STX）包住 → 剥掉头尾后剩下字符串就是码。
  • 矽瞻设备用 [TPL_STX] / [TPL_ETX] 包住 → 同样剥掉再取内容。

1.5 开口数从哪里来的？

PLC 某寄存器里有一个整型（16 位），系统读出来后，会同时更新缓冲垫主表和最新相关明细里的开口数字段。

三、技术调用链路（从「谁触发」到「谁干活」）

看不懂下面代码块也没关系：只要记住 —— 扫码枪线程只负责把「有条码」丢进总线；缓冲垫服务决定怎么记账；PLC 连接对象专门负责读写寄存器。

3.1 谁在什么时候跑？

谁起的头程序里典型位置大白话
服务启动 Connector 初始化 定时尝试重连断开的设备；定时给 PLC 写心跳。
扫码枪发来字节 MsgHandler 认出条码后，往 EventBus 上扔「有条码了」这条消息。
长时间没往枪那边写数据 空闲检测 + HeartbeatHandler 主动给枪发一个心跳包，防止被对端踢下线。
总线上有「条码消息」 CushionInfoServiceImpl 走上一节的业务分支：记账、推 SSE、准备通知 PLC。
总线上有「写 PLC / 读 PLC」 已连上的 Connection（PLC） 先对一下是不是同一条产线，再真正读写寄存器。

3.2 连接建立与总线注册（工程师速查）

下面展示「调连接接口后」在代码里的简化顺序：

接口请求（如连接某产线设备） → Connector.connect → 往 ConnectionMgr 登记 → 若是扫码枪：搭 Netty 管道（编码、空闲、收消息、心跳） → 若是 PLC：用 HSL 连上 → Connection 注册到 EventBus（之后才能收发 PLC 指令） 缓冲垫服务在启动时也会注册到 EventBus，专门消费「扫码」消息。 Connection 断开时会从总线注销，并关掉网络。

3.3 多产线怎么不串？

每条写 PLC、读 PLC 的消息都带产线号；只有产线对得上的那条 PLC 连接才会执行，避免 A 线动作误写到 B 线。

注意：PLC 地址配置里「类型 + 工位号」缺任一都会在代码里查不到地址，结果就是不发 PLC——排障时先查表是否配全。

3.4 前端 SSE 怎么订阅？

连接时传的 clientId 建议等于产线编号字符串。推送时会比对产线，对不上就不发，避免一条线刷屏到另一条线。

四、代码模块一览

目录（包）可以把它理解成
controller对外 HTTP 接口（人点的、大屏调的）
service业务规则、查库、准备推 SSE
netty连扫码枪、维护连接、管道里的解析与心跳
mapper和数据库表打交道
ApplicationContextAwareImpl给「不是 Spring 管的」连接对象，塞一个取 Bean 的旁门（读写 PLC 时要打日志、改缓冲垫）

根地址示例：http://服务器:9001。返回一般是统一的 ResultDTO 包一层（成功 / 失败 / 异常）。

设备 /device · 共 7 个接口
POST/device

在数据库里登记一台设备（枪或 PLC）。

做什么：不会自动连线；只是建档。必填：类型、IP、端口、安装顺序。

调用链
  1. 校验入参 → DeviceInfoServiceImpl.save → 插入 device_info

交接提示：当前保存协议里没有产线字段时，若表里 work_line 不能为空，需与库表约束或接口对一下。

GET/device/devicesPage

分页看设备列表（配置用）。

做什么：纯查库，不带实时在线状态。

调用链
  1. DeviceInfoServiceImpl.listByPage
GET/device/deviceConnections/{workLine}

按产线把库里的设备真的连上（枪走 Netty，PLC 走 HSL）。

做什么：workLine=0 表示不按产线过滤，会把库里设备都尝试连一遍。连上/断开会推 SSE。

调用链
  1. NettyServiceImpl.connectDevices → 查库 → 每个设备 Connector.connect
  2. 内部：ping 通则连；扫码枪建 Netty；PLC 建 HSL 并在成功后注册 EventBus
GET/device/devicesStatus/{workLine}

看一眼内存里当前连线状态，不重新拨号。

做什么：workLine=0 看全部已登记连接。

调用链
  1. ConnectionMgr 取连接 → 转成 DTO
GET/device/scannerConnections

只连所有扫码枪，不动 PLC。

调用链
  1. 筛选 type=扫码器 → 逐个 Connector.connect
DELETE/device/connection/{id}

把内存里的连接拆掉，不动数据库。

调用链
  1. ConnectionMgr.removeConnection
DELETE/device/{id}

库表里删设备，并顺便拆掉内存连接。

调用链
  1. 删库 → removeConnection

六、数据表在业务里扮演什么角色

表可以把它记成
device_info现场有哪几台枪、哪几条线的 PLC，IP 和工位号是多少。
plc_addr「某种信号 + 第几号工位」对应 PLC 上哪一个寄存器地址。
cushion_info每个缓冲垫码的累计使用、上限、最近扫码时间等总账。
cushion_detail每一次有效操作的快照流水。
scan_log给人看的文字日志，排障先用它。
opc_config全局默认值（例如默认最大次数），代码里常按 id=1 取。

七、部署与现场容易踩的坑

  • 各环境数据库、Nacos 等以实际 application-*.yml 为准。
  • PLC 通信依赖自带的 HSL 的 jar，路径别丢。
  • 连设备前会 ping：若现场禁 ICMP，可能出现「永远连不上」的假象。
  • Druid 控制台、Actuator、/test 等对外暴露时要有权限或网络隔离。

若线上行为与本文不一致，以实际运行配置与数据库为准。
