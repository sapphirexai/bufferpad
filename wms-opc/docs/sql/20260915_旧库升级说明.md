# 旧版 wms_opc 升级到当前版本（20260915 修订3账号更正版，交付包 r4）

使用本次压缩包中的 `20260915_upgrade_legacy_to_current.sql`，随后运行 `20260915_upgrade_legacy_verify.sql`。这是包含旧版结构转换和后续新增功能的完整脚本，不需要先执行修订2，也不需要再单独执行日志汇总、清理索引和内置会话迁移。

支持从27旧版六表库、已经执行修订2的数据库、当前新版结构继续升级及重复执行。脚本只操作当前连接选中的数据库，不连接其他服务器，不将27数据合并进149已有业务库。本次交付未在27或149执行升级。

## 相比修订2补齐的内容

| 项目 | 本次处理 |
| --- | --- |
| scan_log.msg | VARCHAR改为TEXT，保留历史消息，支持更长的操作汇总日志及原有默认空字符串写法 |
| 日志汇总字段 | operation_id、operation_type、status、result_code、work_line、operator_name、scanner_id、plc_id、scanner_snapshot、plc_snapshot、detail_json、updated_date |
| 操作唯一索引 | uk_scan_log_operation(operation_id)；旧日志NULL操作ID可并存，不补造历史操作信息 |
| 清理及时间查询索引 | idx_scan_log_created_id(created_date,id) |
| 状态和设备索引 | idx_scan_log_status_time、idx_scan_log_scanner_time、idx_scan_log_plc_time |
| 内置账户登录会话 | 新建sys_builtin_session，仅保存会话摘要及时间；不写入superadmin用户或密码 |
| 防误改预检 | 已有日志字段类型/长度、同名索引定义、已有非空操作ID重复、superadmin数据库同名账户冲突时停止，不静默合并、删除或覆盖 |
| 成功标记 | 完成全部步骤后才输出UPGRADE_OK和版本20260915-r3 |

历史日志主键、二维码、msg、msg_type、created_date（包括毫秒）原样保留。已经产生的新版日志及其设备快照、操作ID、状态、结构化详情也不覆盖。脚本不包含scan_log的INSERT、UPDATE、DELETE，不在升级中清理过期日志。新增列对旧日志保持NULL。

修订2的设备位置、scanner_id关联、PLC地址类型归一化、操作事件字段、账户初始化等转换继续保留。设备/IP/端口/寄存器地址、使用次数、旧寿命配置、历史位置和时间仍遵循保留原则。cushion_detail仅在缺少scanner_id时通过INSTANT追加，在主键窗口内回填缺少的关联，不改旧位置或open_count类型，不复制整个明细表。找不到旧扫码器的历史记录保留空关联，不猜测。

仅当sys_user完全为空时创建默认admin，密码example-admin-password，首次登录无需改密；已有用户、密码、角色、会话、审计和改密要求不被重置。superadmin由当前后端提供，与数据库用户表无关。

## 大表与停写要求

**本版会重建scan_log。** 修订2曾承诺不改变该表结构，此承诺不再适用于修订3：VARCHAR转TEXT需要COPY。对于旧版结构，本脚本把TEXT、所有缺少的汇总字段及五个索引合并为一次ALTER，避免先建索引再重复重建。当前结构已完整时不执行日志表DDL；仅缺索引时使用INPLACE。

执行前停止写入目标库的旧、新后端、扫码采集和清理任务，完整备份并验证可恢复。检查MySQL数据目录和临时目录的可用磁盘空间；建议至少预留当前scan_log数据与索引合计的3倍，并另留备份及运行空间，实际需求取决于磁盘和日志配置。脚本输出SCAN_LOG_PREFLIGHT及表大小估算，但SQL不能代替磁盘空间检查。

元数据锁与行锁等待上限15秒；失败报错，不自动忽略。DDL有隐式提交，不能依赖一次ROLLBACK撤销整个升级。失败后保持停写，排查错误后重跑或恢复备份，不要在仅部分结构完成时启动新版。

明细默认每批5000条，允许在同一连接先设置 `SET @bp_upgrade_detail_batch_size=1000;`（100～20000）。分批已提交的关联保留，中断后重跑会重新遍历窗口但只补空关联。scan_log重建是单次DDL，不能按明细分批参数拆分。

正常六表旧库不会执行日志全表COUNT或业务DML。对于已经存在operation_id、但缺少唯一索引的部分升级库，为防止误建约束，会检查重复非空操作ID；此异常状态下可能扫描现有日志列。同名但定义不一致的索引会报错，需先人工核实，不自动删除。

## 执行方式

数据库基线已于2026-09-15按元数据复核：27为MySQL 8.0.20、6张表，149为MySQL 8.0.42、12张表。脚本适用于这组MySQL 8.0结构。实际DDL验收使用本机MySQL 8.0.45；不将元数据核对描述为在生产8.0.20执行过升级。旧库TABLE_ROWS可为0，不能用此估计判断日志有没有数据。

1. 确认旧库导入已完成，停写并完整备份。只有结构的wms_opc_str.sql不能替代数据备份，也不能当升级脚本直接导入生产。
2. 使用MySQL客户端连接**需要升级的旧库或完整恢复副本**，选择wms_opc数据库，按UTF-8执行本包SQL。不要启用 `--force` 或“遇错继续”。
3. 完成后确认UPGRADE_OK和20260915-r3，再运行只读核验。关联、字段、索引和会话表检查的violations应全部为0；历史未知扫码器单独报告，不视为丢失。
4. 使用当前前后端版本验收登录、用户管理、日志分页、设备/PLC配置及缓冲垫历史记录，确认只有一个采集实例，再恢复生产。

```text
mysqldump --default-character-set=utf8mb4 --single-transaction --routines --triggers --events --hex-blob --set-gtid-purged=OFF --column-statistics=0 -h 192.0.2.6 -P 3306 -u root -p --result-file=wms_opc_before_upgrade.sql wms_opc
mysql --default-character-set=utf8mb4 -h 192.0.2.6 -P 3306 -u root -p wms_opc
```

连接后替换成本机SQL路径执行：

```sql
SOURCE C:/path/to/20260915_upgrade_legacy_to_current.sql;
SOURCE C:/path/to/20260915_upgrade_legacy_verify.sql;
```

若最终运行在149，先将27完整备份恢复到149的独立空库，在恢复库运行本脚本并验收后切换应用连接。不要覆盖149当前正在使用的wms_opc库。

**升级SQL不会删除旧日志，但当前后端默认每天03:00执行最近三个月保留策略。** 为核对完整旧历史，隔离验收或恢复验证期间可设置 `SCAN_LOG_RETENTION_ENABLED=false`，正式运行再按约定启用。日志分页已经在当前应用实现，修订2报告中的“日志接口无分页”属于历史版本限制，不是当前版本行为。

完整验收范围和结果见同包 `20260915_旧库升级验收.md`。项目原链接文件名20260914_upgrade_legacy_to_current.sql及verify.sql已同步到修订3；以前下载的r2压缩包不会自动更新，请重新下载本次r3包。
